# Nix style

This adds to `coding-style`, which applies too. It is my style, for my projects.
On a project that is not mine, follow that project's own style.

## Readability over brevity

The rules in this section make Nix code a bit more verbose on purpose. More
verbose is not a problem for me. Less readable is. The goal is that you can
always see where a name comes from.

Many of these are common idioms in Nix, and I do not want those idioms. There
are no idiomatic exceptions to the rules in this section.

- **Never use `with`.** Repeat yourself and write the full name each time, for
  example `pkgs.git`.
- **Never use `rec`.** Use `let ... in`. Order the bindings by what depends on
  what: a binding comes after the ones it uses.

  ```nix
  let
    a = 1;
    b = a + 2;
    c = b + 3;
  in
  c
  ```

- **Always prefix builtins with `builtins.`.** Write `builtins.map` and not
  `map`. This covers all of them, including `import`, `throw`, `abort` and
  `toString`. Never name a variable the same as a builtin.
- **Never leave unused variables, arguments or `...`.** A lambda that ignores
  its attrset argument takes `_` and not `{ ... }`. A module that takes no
  arguments is a plain attrset, because an attrset is also a module. So
  `{ ... }: { module content }` is wrong and `{ module content }` is right. This
  is about a function that takes nothing, not about the `...` in
  `{ lib, config, ... }:`. A module that takes arguments needs that `...`,
  because the module system passes more arguments than it uses, and it stays.
  Still list only the arguments the module uses.

## File order

This adds to File order in `coding-style`. Nix is a partial exception to it,
because `let ... in` has to come first. So:

1. First order by `let ... in` dependencies: a binding comes after the ones it
   uses, as above.
2. Then order everything else in the file from high level to low level, as in
   `coding-style`.

So helpers in a `let` above the module body are fine. What follows `in` still
reads from the main idea down to the details.

## Assets

An asset is any file a module uses that is not another module: a shell script, a
config template, a preset, a `2nix` lock file, and so on.

- An asset used by one module sits right next to it, in a folder named after the
  module. The module itself is the `default.nix` in that folder. So module `foo`
  is `foo/default.nix`, and its assets are `foo/<asset>`.
- An asset used by more than one module goes into the top-level `assets/` folder
  of the repository. When a second module starts using an asset, move it there.

When an asset needs values from Nix, render it with
`pkgs.harasPackages.renderMustache` (a package) or
`pkgs.harasPackages.renderMustacheText` (the contents), and not with
`pkgs.replaceVars`. Mustache is more flexible, so the asset file is rendered
straight from Nix data. Shell scripts are the one case that works the other way
around, see the next section.

## Shell scripts

A tiny snippet can stay inline in the Nix string. Anything longer is an asset,
as above. There is no hard line for tiny: a single command with a flag or two is
tiny, and a script with branching, loops or functions is not. Use your judgment.

Write scripts in Nushell, with `pkgs.harasPackages.writeNushellApplication`. Use
another shell only when you absolutely must, and say why in a comment (see
`coding-style`).

To get values from Nix into a script, render the asset with the same mustache
helpers as any other asset, but with the data torn apart in the shell and not
the shell code generated by the template. I would rather parse data in the shell
than build shell code from a template. So the template only holds values, and
the logic stays plain script. Use triple braces, so nothing is escaped, inside a
Nushell raw string:

```nu
let my_var = r#'{{{nameOfVarFromNix}}}'#
let my_list = r#'{{{listFromNix}}}'# | from json
```

Pass a string as it is. Pass any other value through `builtins.toJSON` in Nix
and add `| from json` in the script, which turns it back into a Nushell data
structure.

Other shells follow the same pattern, with that shell's own raw string quoting
and JSON parsing.

## Tooling

I use `nixfmt` and `nil`.

- Any format command formats with `nixfmt`.
- Any check command runs `nil diagnostics` and exits 1 if it reports anything.

`nixfmt` does not read `.editorconfig`, so the 80 columns are passed to it as
`--width 80`. Its indentation is already 2 spaces.

## Flakes

Every repository is a flake, built on
[haraspkgs](https://github.com/haras-unicorn/haraspkgs). The
`new-haraspkgs-project` skill covers setting one up, including the dev shell.

- The top-level expression of every `.nix` file in a flake is a flake-parts
  module. The exception is a small flake that only needs a `flake.nix`.
- In a repository with more than a `flake.nix`, all the Nix goes into `src/nix`,
  always. `makeFlake` gets `./src/nix`.
- Use the options haraspkgs provides as much as possible. They all start with
  `self`.
- If you need to use flake-parts directly to get around a missing option, tell
  me and add it for now. Put a comment next to it that says why haraspkgs could
  not do it. Do not leave a `TODO`, because that goes into an issue. Then tell
  me which flake introduced the bypass, why it was needed, and how to adopt the
  solution in haraspkgs, so I can write the haraspkgs issue.

## Testing

The general rules are in `coding-style`, and the layout follows what Rust does:
unit tests sit next to the code, integration tests are apart in their own
folder. With haraspkgs:

- Unit tests use `nix-unit` through `self.unitTests`, in the same file as the
  library functions they test:

  ```nix
  self.unitTests.<module-name>.<test-name> = {
    expr = 1;
    expected = 1;
  };
  ```

- Integration tests live in their own folder, `src/nix/tests/`, and not next to
  the modules. They depend on the module system. NixOS tests go through
  `self.nixosTests`, which also work for home-manager. The `value` is a function
  that returns a NixOS test module, and `flake = true` makes it a check:

  ```nix
  self.nixosTests.example = {
    flake = true;

    value =
      _:
      {
        containers.agent = { };

        testScript = ''
          start_all()
          agent.succeed("true")
        '';
      };
  };
  ```

- Dev module tests go through `self.devTests`. They are written in haraspkgs
  itself, and the instructions are in the working directory there.
- An integration test only checks that the module, which is the facade, works
  with that service.

## Documentation

All the documentation is in the repo's mdbook (see `coding-style`). The options
you add get docs there, and those are generated and checked and not written by
hand:

- The format command generates them with `nix build`, using the haraspkgs docs
  helpers (`mkOptionsDocs`), and writes them into the mdbook.
- The check command builds them again and checks that they equal what is
  committed.
- Both run the generated docs through the repo's markdown formatter first,
  before writing or comparing. That is almost always prettier.

## Tunables

Module options with defaults are the Nix form of tunables (see `coding-style`).
A magic value in a module becomes an option, and the default is the value you
wanted to set.
